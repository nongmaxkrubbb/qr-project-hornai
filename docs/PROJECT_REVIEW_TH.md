# แผนพัฒนาโครงการสั่งอาหารในหอพักและมหาวิทยาลัย

ประเมินวันที่ 21 กันยายน 2026 จากโค้ดที่ commit `ce9f9f0` เป้าหมายที่ผู้ใช้ยืนยันคือเปิดใช้จริงในหอหรือมหาวิทยาลัย แล้วขยายหลายร้าน

**ข้อเสนอหลัก:** พัฒนาให้เป็นระบบ “สั่งก่อน มารับเมื่อพร้อม ร้านจัดการช่วงพีกได้” โดยพิสูจน์ผลกับร้านแรกก่อน ข้อได้เปรียบที่จะสร้างได้คือความแม่นยำของคิว ความง่ายในการทำงานของร้าน และขั้นตอนเปิดร้านใหม่ที่ทำซ้ำได้

สถานะปัจจุบันเป็นต้นแบบที่มีเส้นทางสั่งอาหารค่อนข้างครบ แต่ยังมีข้อบกพร่องด้านสิทธิ์ ออเดอร์ และการรับเงินที่ควรแก้ก่อนเปิดรับลูกค้าจริง การมีตารางหลายสาขายังไม่ยืนยันว่าระบบแยกข้อมูลหลายร้านได้ถูกต้อง

**ขอบเขตและหลักฐานการตรวจ:** อ่าน Python routes, configuration, schema/migration, templates และสคริปต์ทดสอบ ตรวจ syntax ของ Python หลัก 8 ไฟล์และ compile Jinja templates 10 ไฟล์สำเร็จ ทดสอบ Flask ด้วยข้อมูลจำลองโดยปิดการเชื่อมต่อ network และทดสอบฟังก์ชันบางส่วนด้วย AST extraction/in-memory mocks ไม่ได้ตรวจฐานข้อมูล production, grants, bucket settings, อุปกรณ์จริง หรือรับรองความสามารถรองรับโหลดจริง งานนี้เพิ่มรายงานเท่านั้น

**สิ่งที่มีและควรต่อยอด**

- ลูกค้าสั่งโดยไม่ต้องสมัครสมาชิก: เมนู → ตะกร้า → เงินสด/PromptPay → ติดตามออเดอร์
- ร้านมีบอร์ดรอคิว/กำลังทำ/พร้อมรับ การจัดการเมนู และ dashboard
- ฐานข้อมูลมี organizations, branches, staff roles และเวลาสร้าง/เริ่มทำ/พร้อมรับ/รับแล้ว
- เลขคิวใช้ database function แบบ atomic; รายการอาหารเก็บชื่อและราคาขณะสั่งไว้แล้ว
- มี Supabase Auth, CSRF และ audit log เป็นฐานสำหรับทำระบบให้เชื่อถือได้

Flask + Jinja + Supabase ยังเป็นฐานที่เหมาะกับการทดลองและพัฒนาต่อ ควรแยก business logic ออกจาก routes และวัดคอขวดจริงก่อนตัดสินใจเปลี่ยนเทคโนโลยี

เริ่มด้วยการตรวจโอนโดยพนักงานที่มีปุ่มยืนยัน/ปฏิเสธชัดเจน และปุ่มรับเงินสดจริง ให้ลูกค้าเห็นผลตรวจและเหตุผลที่ต้องแก้ ระบบควรบันทึกผู้ตรวจ เวลา ยอด วิธีรับเงิน และเหตุผลยกเลิก การแนบรูปเป็นเพียงหลักฐานรอตรวจ ไม่ใช่ผลยืนยันว่าได้รับเงิน

เก็บสลิปใน private bucket และให้พนักงานที่มีสิทธิ์เปิดผ่าน URL อายุสั้น แยกการตรวจไฟล์ฝั่ง server ออกจาก `accept="image/*"` ซึ่งเป็นเพียงตัวช่วยของ browser ปัจจุบันโค้ดใช้ `get_public_url` แต่ repository ไม่ยืนยันว่า bucket จริงตั้งค่าอย่างไร แนวทาง private bucket และ signed URL มีใน [เอกสาร Supabase Storage](https://supabase.com/docs/guides/storage/buckets/fundamentals)

สำหรับแจ้งเตือนเมื่อไม่ได้เปิดหน้า ต้องออกแบบ Web Push และทดสอบอุปกรณ์จริง โดยบน iOS/iPadOS มีเงื่อนไข Home Screen web app และการขออนุญาตจากการกดของผู้ใช้ตาม [เอกสาร WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) ควรมีปุ่มเปิดแจ้งเตือนพร้อมข้อความบอกสถานะการรองรับ และมีวิธีติดตามสำรองก่อนใช้ข้อความรับประกันการแจ้งเตือน

**โครงสร้างสำหรับขยายหลายร้าน**

รักษาหนึ่งร้านต่อออเดอร์ แล้วเพิ่ม directory ร้านตามหอ/มหาวิทยาลัย เมื่อเปลี่ยนร้านให้เก็บตะกร้าแยกหรือแจ้งก่อนเปลี่ยน ทุกหน้าต้องแสดงชื่อร้านและจุดรับอย่างชัดเจน ปัจจุบันชื่อหน้าเมนูตายตัว และ `PROMPTPAY_ID` เป็น environment กลางทั้งระบบ: [payment page](/Users/nongmax/Desktop/qr-project-v2/app/routes/user_routes.py:238)

ก่อนเปิดร้านที่สองต้องมีข้อมูลชื่อร้าน เวลาเปิด จุดรับ บัญชีรับเงิน และเจ้าหน้าที่แยกตามร้าน บัญชีรับเงินต้องตรวจและตั้งค่าโดยผู้มีสิทธิ์ พร้อมประวัติการเปลี่ยนแปลง หากยังไม่ตั้งค่าถูกต้องให้ปิดการรับโอนของร้านนั้นแทนใช้เลข default

แยกความหมายของเจ้าของร้าน/องค์กรออกจากสถานที่ตั้งมหาวิทยาลัยให้ชัด ร้านหลายเจ้าของอยู่ในมหาวิทยาลัยเดียวกันไม่ได้หมายความว่าทุกเจ้าของควรเห็นข้อมูลกัน ผู้ดูแลพื้นที่ควรได้เฉพาะข้อมูลที่กำหนดสิทธิ์ไว้

โครงสร้างที่เสนอคือ Browser → Flask ตรวจสิทธิ์และข้อมูล → service layer → Supabase/Postgres โดยให้ RPC สร้างออเดอร์และเปลี่ยนสถานะทำงานแบบ transaction และจำกัดสิทธิ์เรียก RPC ฝั่ง server ให้ตรงกับงาน ใน repo ค่อยแยก `orders`, `payments`, `authorization` ออกจาก routes เพื่อลดการเขียนเงื่อนไขสำคัญซ้ำ

เมื่อใช้หลาย process ให้ counter ของ rate limiter อยู่ใน shared storage เพราะ `memory://` แยกต่อ process และหายเมื่อ process จบ ตาม [เอกสาร Flask-Limiter](https://flask-limiter.readthedocs.io/en/stable/configuration.html) ส่วน cache เมนูต้องมีกติกา invalidate เมื่อร้านปิดเมนู และยังตรวจความพร้อมขายซ้ำตอน checkout เสมอ

**รายงานและการดูแลระบบที่ต้องตามมา**

- แยกมูลค่าออเดอร์ ยอดรับเงินจริง ยอดค้าง และคืนเงิน; dashboard ปัจจุบันรวมทุกออเดอร์ที่ไม่ cancelled เป็นรายรับที่ [admin_routes.py](/Users/nongmax/Desktop/qr-project-v2/app/routes/admin_routes.py:292)
- รวมยอดด้วย SQL และกำหนดช่วงเวลาตาม timezone ร้าน ปัจจุบันใช้ date.today() ของ server ทั้งเลขคิวและ dashboard
- หลีกเลี่ยง aggregate จากรายการที่ดึงมาไม่ครบ ปัจจุบัน query ไม่มี pagination และ Supabase มีค่าเริ่มต้นส่งกลับสูงสุด 1,000 แถวตาม [เอกสาร Python select](https://supabase.com/docs/reference/python/select) ค่าใช้งานจริงต้องตรวจในโปรเจกต์
- เก็บ request ID, order ID, branch ID ใน log; ติดตาม 5xx/429, checkout latency, ออเดอร์ค้าง, งานรับเงินค้าง โดยไม่บันทึก token หรือข้อมูลสลิปที่ไม่จำเป็น
- ให้ session ถูกเพิกถอนเมื่อปิดบัญชี/เปลี่ยนสิทธิ์ ปัจจุบันตรวจ is_active เฉพาะตอน login
- แก้การใช้ innerHTML กับชื่อเมนูจากข้อมูลในหน้า status เป็น textContent/DOM ที่ปลอดภัย ตรวจราคา/จำนวนและชนิด payment ด้วย server validation และ DB constraints
- จัด staging แยก production, migration มีลำดับ, dependency versions ที่ทำซ้ำได้, backup และซ้อม restore ก่อนเปิดจริง
- README ต้องตรงกับระบบ: ปัจจุบันบอก DATABASE_URL ทั้งที่ใช้ Supabase API, ใช้ --username ทั้งที่ script ต้องการ --email, ไม่พบ .env.example, ไม่ระบุขั้นตอน payment migration/bucket และบอกว่ายังไม่ใช้ Realtime ทั้งที่ใช้แล้ว
- สคริปต์ test*.py เดิมส่วนใหญ่เรียก service จริงหรือ insert ข้อมูลและ print ผล ไม่ใช่ regression suite ที่แยกสภาพแวดล้อม ควรจัดชุด tests ใหม่ให้ปลอดภัยต่อการรันใน CI

**แผนทดลองกับร้านจริง**

เลือกร้านที่มีคิวช่วงพีกและพนักงานพร้อมร่วมทดลอง สังเกตงาน 2–3 ช่วงขายก่อนเปิดระบบ วัดเวลามาถึงหน้าร้านจนรับอาหาร จำนวนออเดอร์ต่อชั่วโมง การถามคิว และออเดอร์ผิด จากนั้นเริ่มหนึ่งช่วงพีกต่อวัน เก็บปัญหาแยกตามออเดอร์และทบทวนกับร้านหลังปิดช่วงขาย

ซ้อมกรณีลูกค้ากดซ้ำ เน็ตหลุด เมนูหมด โอนผิดยอด ไม่มารับ ยกเลิก และเครื่องครัวใช้งานไม่ได้ เตรียมวิธีหยุดรับออนไลน์และจดงานคงค้างชั่วคราว แล้วนำกลับเข้าระบบโดยตรวจไม่ให้สร้างซ้ำ พร้อมระบุผู้ช่วยที่ร้านติดต่อได้

| Metric | วิธีวัด | เป้าทดลองเบื้องต้น |
|---|---|---|
| ออเดอร์รับสำเร็จโดยไม่ต้องช่วยแก้ | completed พร้อม incident flag; รายงาน no-show/ยกเลิกแยก | อย่างน้อย 98% ของออเดอร์ที่ร้านรับทำ โดยตกลงนิยามกับร้านก่อน |
| เวลายืนรอหน้าร้าน | สุ่มวัดเวลามาถึงกับรับจริง; ใช้ median และ p90 | median ลดลง 30% จาก baseline |
| ความแม่น ETA | เก็บเวลาที่สัญญาขณะยืนยัน เทียบ ready_at | ตั้งช่วงยอมรับหลังเห็นข้อมูลร้านจริง |
| ความถูกต้องของเงิน/ร้าน | ตรวจรายการรับเงินกับออเดอร์และผู้รับเงินรายวัน | ไม่มีรายการผิดร้านหรือยอดไม่ตรงที่ยังอธิบายไม่ได้ |
| ร้านใช้ต่อเอง | วันเปิดใช้งาน, สัดส่วนออเดอร์เข้าระบบ, จำนวนครั้งต้องให้ผู้พัฒนาช่วย | ใช้เองต่อเนื่องอย่างน้อย 5 วันขายก่อนขยาย |
| ต้นทุนดูแล | hosting, storage, notification/payment fees ถ้ามี, เวลาช่วยร้าน | วัดต่อร้าน/เดือนและต่อออเดอร์ก่อนตั้งราคา |

ตัวเลขข้างต้นเป็นเป้าตั้งต้นสำหรับตกลงกับร้าน ไม่ใช่ผลการทดลองที่เกิดขึ้นแล้ว `created_at → completed_at` ไม่ใช่เวลายืนรอ เพราะลูกค้าอาจยังอยู่หอ ต้องวัดเวลามาถึงหน้าร้านแยก

**สิ่งที่ทำให้เติบโตต่อได้หลัง pilot**

1. ทำแพ็กเกจเปิดร้านใหม่ที่ครบ: ตั้งร้านและเจ้าหน้าที่ → เมนูและบัญชีรับเงิน → QR ร้าน → ทดลองสั่ง/รับเงิน → สอนครัว → ช่องทางช่วยเหลือ วัดเวลาที่ใช้เปิดร้านใหม่ทุกครั้ง
2. ขยายเป็นกลุ่มร้านในพื้นที่เดียวกัน เพื่อให้การแนะนำระบบและช่วยเหลือทำได้สะดวก เก็บผลเวลารอ/ออเดอร์ที่ร้านอนุญาตให้ใช้เป็นตัวอย่างในการชวนร้านถัดไป
3. เมื่อคิวมีข้อมูลจริง เพิ่มการจองเวลารับและจำกัดจำนวนรับต่อช่วง โดยเชื่อมกับกำลังครัวและ walk-in ไม่เปิดรับล่วงหน้าแบบไม่จำกัด
4. เพิ่มรูป/ตัวเลือกต่อจานและสั่งซ้ำเมื่อข้อมูลบอกว่าคนใช้ติดขัดตรงนั้น ส่วนระบบแนะนำอาหารควรเริ่มจากเมนูขายดีและความพร้อมขายก่อน
5. หลังร้านเห็นประโยชน์และทีมรู้ต้นทุน จึงทดลองค่าบริการต่อร้านหรือผู้สนับสนุนระดับหอ/มหาวิทยาลัย โดยสัมภาษณ์ผู้จ่ายเงินจริงก่อนเลือกโมเดลและราคา

ยังไม่มีข้อมูลจำนวนลูกค้า ยอดขายจริง ค่าใช้จ่าย production หรือความยินดีจ่าย จึงไม่สามารถคาดการณ์รายได้หรือจำนวนร้านที่จะรองรับได้อย่างมีหลักฐาน จุดพิสูจน์แรกคือร้านหนึ่งใช้เองได้ นักศึกษารอน้อยลง และออเดอร์กับเงินตรวจสอบได้ครบ
