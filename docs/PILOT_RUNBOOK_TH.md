# คู่มือเปิดร้านแรกและขยายหลายร้าน

เอกสารนี้เป็นขั้นตอนปฏิบัติและแบบเก็บข้อมูล ยังไม่ใช่ผลทดลองกับร้านจริง

## เตรียมก่อนเปิดขาย

1. ตกลงร้านนำร่องหนึ่งร้านและช่วงทดลอง มีผู้ตัดสินใจเรื่องเมนู/เงิน/ยกเลิกและผู้ช่วยแก้ปัญหาที่ติดต่อได้
2. วัด baseline อย่างน้อย 2–3 ช่วงพีก: เวลามาถึงจนรับของ จำนวนออเดอร์ต่อชั่วโมง คิวผิด จำนวนคนถามคิว และเวลาพนักงานใช้จัดออเดอร์
3. เปิดองค์กร/ร้านที่ถูกต้อง แยกเจ้าของกิจการออกจากสถานที่ตั้งมหาวิทยาลัย ตั้งบัญชี staff ตามสาขาและทดสอบว่าเข้าร้านอื่นไม่ได้
4. ให้เจ้าของร้านตรวจชื่อผู้รับเงินและ PromptPay ด้วยตนเอง ตั้งเวลาเปิด จุดรับ ระยะเวลาทำเฉลี่ย และจำนวนงานครัวที่ทำพร้อมกัน
5. เพิ่มเมนู/ตัวเลือก/ราคา ซ้อมสั่งเงินสดและโอนครบถึงรับแล้ว ตรวจรายงานและคืนเงินด้วยยอดทดสอบที่ร้านอนุมัติ
6. ตั้ง `PUBLIC_BASE_URL` เป็นโดเมนจริง แล้วเข้าเมนู **QR ร้าน** เพื่อพิมพ์ป้ายลิงก์หน้าร้าน `/b/BRANCH_UUID` ให้ลูกค้าเข้าเมนู เก็บ QR ติดตามออเดอร์เป็นส่วนตัวและอย่าติดประกาศสาธารณะ
7. ใช้ walk-in รับออเดอร์หน้าร้านเข้าคิวเดียวกัน ตั้งปุ่มเปิดเสียงบนจอครัวด้วยการกดของผู้ใช้ก่อนเริ่มขาย
8. เริ่มเฉพาะช่วงทดลองที่ตกลงกัน หากงานล้นให้กดพักรับออเดอร์ งานที่รับแล้วต้องทำต่อและติดตามให้จบ

## ซ้อมเหตุการณ์

| เหตุการณ์ | วิธีจัดการ |
|---|---|
| ลูกค้ากดยืนยันซ้ำ/เน็ตหลุดหลังสั่ง | เปิดออเดอร์ของฉันก่อนสั่งใหม่ ระบบใช้ key เดิมคืนออเดอร์เดิม; ถ้าไม่แน่ใจให้ร้านตรวจจากเวลา/ชื่อ/ยอด |
| เมนูหมด | ปิดขายเมนูทันที รายการในตะกร้าจะตรวจซ้ำตอนยืนยัน; แจ้งเหตุผลก่อนยกเลิกรายการที่รับแล้ว |
| สลิปตรวจไม่ผ่าน | ระบุเหตุผลและกดปฏิเสธ ลูกค้าเห็นคำอธิบายและส่งใหม่ได้ภายในเวลาที่กำหนด |
| ลูกค้าโอนหลังหมดเวลา | อย่าสั่งให้ลูกค้าโอนซ้ำ ตรวจเงินกับธนาคาร/ผู้รับ บันทึก incident และจัดการคืนเงินหรือสร้างรายการใหม่ตามที่ตกลง |
| เงินสด | กดรับเงินสดเมื่อรับเงินจริงก่อนปิดออเดอร์ แม้ร้านอนุญาตเริ่มทำก่อนจ่าย |
| ยกเลิกหลังชำระแล้ว | ระบบขึ้นรอคืนเงิน ให้ผู้มีหน้าที่คืนเงินจริงนอกระบบ แล้วบันทึกคืนเงินพร้อมเหตุผล; ปุ่มนี้ไม่ได้โอนเงินแทนร้าน |
| ไม่มีคนมารับ | ติดต่อผ่านช่องทางที่ลูกค้าให้ร้านไว้ถ้ามี บันทึก incident; ไม่อ้างว่าลูกค้ารับแล้วเพื่อปิดคิว |
| อินเทอร์เน็ต/จอครัวใช้ไม่ได้ | พักรับออนไลน์เมื่อทำได้ จดรายการคงค้างและเวลา เก็บเลขออเดอร์เดิม กลับมาแล้วตรวจรายการก่อนเพิ่ม walk-in ป้องกันงานซ้ำ |
| ร้านปิดรับระหว่างวัน | กดพักรับงาน ไม่ยกเลิกออเดอร์เดิมอัตโนมัติ |
| การแจ้งเตือนไม่ทำงาน | ให้ดูหน้าสถานะล่าสุด ตรวจสิทธิ์ browser/การติดตั้ง Home Screen; ฝั่งระบบตรวจ worker/outbox โดยไม่เก็บ token ใน log |

## ปิดยอดทุกวัน

- เทียบเงินสดที่รับจริงกับรายการเงินสดที่ยืนยันแล้ว และเงินเข้าบัญชีกับเลขอ้างอิงที่ตรวจ
- แยกมูลค่าออเดอร์ ยอดรับจริง ยอดค้าง รอคืนเงิน คืนแล้ว และข้อมูลเก่ารอตรวจ (`legacy_unverified`)
- Dashboard ของออเดอร์วันที่เลือกกับยอดรับเงินวันที่เลือกเป็นคนละมุมมอง โดยเฉพาะจ่ายข้ามวัน
- ตรวจ incident และรายการที่ยังไม่จบ ระบุคนรับผิดชอบและนัดติดตามก่อนเริ่มวันถัดไป
- ตรวจ 5xx/429 และ checkout latency จาก monitoring ของ hosting ตั้งแจ้งเตือนเมื่อเกิน baseline ที่วัดได้จริง

## ตัวชี้วัดและเกณฑ์ขยาย

ใช้ `pilot_measurements.csv` เก็บตัวอย่างก่อน/หลัง โดยไม่ใส่ชื่อ ห้อง หรือภาพสลิป เปลี่ยนเฉพาะรหัสร้าน/ออเดอร์และเวลา ใช้เวลาท้องถิ่นพร้อม timezone

- เวลายืนรอ = รับอาหารจริง − มาถึงจุดรับ; ไม่ใช้เวลาตั้งแต่กดสั่งแทน Dashboard มี arrived_at จากปุ่มลูกค้ามาถึงแล้ว แต่ควรสุ่มวัดหน้างานประกอบ
- เวลารอเริ่มทำ = started_at − created_at; แยกออเดอร์จองเวลารับออกจากคิวทันที
- เวลาทำ = ready_at − started_at และเวลารอรับ = completed_at − ready_at
- ความคลาดเคลื่อน ETA = ready_at เทียบ promised_ready_at; ดู median/p90 และรายการผิดปกติ
- ติดตามออเดอร์รับสำเร็จโดยไม่ต้องช่วยแก้ ยกเลิก/no-show เงินไม่ตรง จำนวนวันร้านใช้งานเอง และต้นทุนช่วยเหลือต่อร้าน

เป้าตั้งต้นสำหรับตกลงกับร้าน: median เวลายืนรอลดลง 30%, ออเดอร์ที่ร้านรับทำจบโดยไม่ต้องช่วยแก้อย่างน้อย 98%, กระทบยอดทุกวัน และร้านใช้งานเองได้ 5 วันขายติดต่อกัน ตัวเลขนี้ต้องปรับตามข้อมูลจริง

ขยาย 1 → 2 → 5 ร้านเมื่อไม่มีเหตุข้อมูล/เงิน/ออเดอร์ผิดร้านที่ยังไม่แก้ ร้านเดิมยังใช้ต่อเอง และทีมช่วยเหลือดูแลไหว เปิดการจองเวลารับทีละร้านหลังวัดกำลังครัว โดยตั้ง slot_capacity ให้รวมภาระหน้าร้านด้วย

## ทำให้เปิดร้านใหม่ได้ซ้ำ

ใช้รายการเดียวกันทุกครั้ง: เจ้าของกิจการ → สาขาและเจ้าหน้าที่ → เมนู/ราคา → บัญชีรับเงิน → เวลา/จุดรับ/กำลังครัว → ทดลองครบวงจร → ฝึกใช้ → เปิดช่วงทดลอง → ปิดยอดวันแรก บันทึกเวลาที่ใช้ onboarding และเหตุที่ต้องให้ผู้พัฒนาช่วย แล้วปรับขั้นตอนก่อนเพิ่มร้าน

โมเดลค่าบริการและผู้จ่ายเงินระดับหอ/มหาวิทยาลัยยังต้องสัมภาษณ์และทดลองกับผู้เกี่ยวข้อง ไม่ได้ตั้งราคาหรือเรียกเก็บเงินในรอบนี้
