# สิ่งที่พัฒนาและขั้นตอนนำไปใช้งาน

รอบพัฒนานี้ต่อยอดจากรายงาน PROJECT_REVIEW_TH.md ซึ่งเป็น snapshot ก่อนแก้ ไม่ควรใช้เลขบรรทัดในรายงานเดิมอ้างโค้ดปัจจุบัน

## งานที่ทำใน repository

- สร้างออเดอร์ผ่าน RPC transaction พร้อมตรวจสาขา เมนู ตัวเลือก ราคา โควตารับล่วงหน้า และ idempotency
- Capability token ที่เก็บเป็น hash ใน DB ใช้กับติดตาม จ่ายเงิน อัปโหลด ยกเลิก มาถึง และสั่งซ้ำ
- ปิด public table reads และ public slips bucket; ตรวจภาพ/ขนาดก่อนเก็บและชดเชยไฟล์กำพร้าเมื่ออัปเดตสถานะไม่ได้
- สิทธิ์ staff โหลดใหม่ทุก request แยกร้าน/องค์กร fail closed พร้อมตรวจซ้ำใน RPC และ audit
- สถานะครัวแยกจากการรับเงิน เพิ่มยืนยัน/ปฏิเสธหลักฐาน รับเงินสด ยกเลิก รอคืนเงิน และบันทึกคืนเงินจริง
- หน้าเลือกร้าน ตะกร้าแก้ไข ตัวเลือกต่อจาน สั่งซ้ำ เวลาเปิด จุดรับ ตั้งค่าร้าน และบัญชีรับเงินต่อสาขา
- หน้าพิมพ์ QR ร้านสำหรับติดป้าย และ QR ติดตามออเดอร์ส่วนตัวที่ใช้ capability token
- หน้าครัว tablet อัปเดตเฉพาะส่วน ออเดอร์หน้าร้านในคิวเดียว ปุ่มพักรับ เสียงเปิดโดยผู้ใช้ และบันทึกเหตุขัดข้อง
- ETA รวมงานของออเดอร์ตัวเองตามกำลังครัวและเวลาเตรียมที่ร้านกำหนด พร้อมเก็บเวลาที่สัญญาเพื่อวัดความแม่นยำ
- Polling ที่มี backoff/สถานะออฟไลน์/อัปเดตเมื่อกลับมาเปิดหน้า และ Web Push ผ่าน service worker + durable outbox + worker
- SQL dashboard ตาม timezone, การวัดมาถึง/เวลาเตรียม/เวลารับ/incident และการตั้งค่าจองช่วงเวลารับแบบจำกัดโควตา
- Shared production rate limiter, CSRF, private cache headers, safe logs, health/readiness, provisioning scripts และ CI tests
- คู่มือ rollout, baseline/pilot CSV และเกณฑ์ขยายจำนวนร้าน

## งานเก็บรายละเอียดเพื่อเปิดใช้งาน

- ย้ายตะกร้าและประวัติไป server-side session เพื่อหลีกเลี่ยงคุกกี้ขนาดเกิน; Redis สำหรับ production และไฟล์ภายใน instance สำหรับ development
- แยกอายุประวัติลูกค้า 35 วันออกจากสิทธิ์พนักงาน 8 ชั่วโมง พร้อมเปลี่ยน session ID เมื่อเข้าสู่ระบบ/ออกจากระบบ
- เก็บชื่อ/บัญชีรับเงินขณะสั่งไว้กับออเดอร์ กันใช้เลขโอนซ้ำข้ามสาขาที่รับเงินบัญชีเดียวกัน และกันยืนยันสลิปที่เปลี่ยนหลังเปิดแบบฟอร์ม
- ห้ามส่งสลิปทับขณะกำลังตรวจ แก้การหมุนภาพจากโทรศัพท์ และไม่สร้าง QR ชำระซ้ำเมื่อจ่ายสำเร็จแล้ว
- หน้าเลือกร้านอ่านจำนวนคิวจริงพร้อมกันผ่าน RPC และตัวกรองมหาวิทยาลัยไม่หายเมื่อเลือกพื้นที่แล้ว
- หน้าสถานะแสดงข้อมูลเริ่มต้นจาก server และเวลาออเดอร์แสดงตาม timezone ร้าน
- Worker จัดการออเดอร์หมดอายุได้โดยไม่ต้องเปิด push และ retry เมื่อบริการขัดข้องชั่วคราว
- เพิ่มคำสั่งสร้างองค์กร Dockerfile/Compose พร้อม Redis/worker และตัวเลือก HTTPS ผ่าน Caddy
- ติดตั้ง dependencies ลง `.venv` ใน workspace แล้ว ค่า Supabase ที่แอปต้องใช้ครบใน `.env` แต่ไม่มี SQL connection/Management API สำหรับติดตั้ง schema จากเครื่องนี้

รอบนี้ไม่สร้าง แก้ไข หรือรันทดสอบใด ๆ ตามคำขอ งานฐานข้อมูลและการ deploy ยังเป็นไฟล์สำหรับนำไปติดตั้ง ไม่มีการเปลี่ยน Supabase จริง

## สิ่งที่ต้องตั้งค่าหรือลงมือในสภาพแวดล้อมจริง

ยังไม่ได้รัน migration บน Supabase จริงหรือ deploy production เพราะงานพัฒนาครั้งนี้ทดสอบในสภาพแวดล้อมแยก ไม่มีการเปลี่ยนข้อมูลลูกค้าหรือร้านจริง

1. สำรอง DB แล้วทดสอบ migration บน staging; ตรวจข้อมูลเก่าและ staff scope ตาม DATABASE.md
2. ตั้ง ENV, HTTPS, Redis, domain/proxy และ deploy code/migration ในช่วงเปลี่ยนระบบเดียวกัน
3. ให้ร้านยืนยันผู้รับเงินและตรวจรายการเดิม; ลิงก์เลข ID เดิมไม่มี token จึงเปิดเป็น public ไม่ได้แล้ว
4. ถ้าใช้ push ให้สร้าง VAPID ตั้งทั้ง 3 ค่า เปิด worker และทดสอบบนมือถือจริง; การสมัคร subscription อย่างเดียวไม่ทำให้เกิดการส่ง
5. ซ้อมด้วยฐานข้อมูล/Storage/Auth ของ staging รวมการอัปโหลดและ signed URL; PGlite จำลอง SQL ได้ แต่ไม่จำลองบริการ Supabase เหล่านี้ครบ
6. ทดสอบโหลดหลาย connection บน PostgreSQL จริงและ topology Redis/proxy ของที่จะ deploy ก่อนระบุจำนวนร้าน/ผู้ใช้ที่รองรับ
7. ทดลองร้านจริงและเก็บ baseline/KPI ตาม PILOT_RUNBOOK_TH.md ตัวเลขเป้าหมายยังไม่ใช่ผลที่พิสูจน์แล้ว

การตรวจสลิปยังเป็นงานของพนักงาน ไม่ได้ต่อธนาคารหรือบริการตรวจสลิปอัตโนมัติ ปุ่มคืนเงินเป็นการบันทึกว่าร้านคืนเงินจริงแล้ว ไม่ได้สั่งโอนเงิน การคาดเวลายังใช้กติกาที่อธิบายได้จากกำลังครัวและคิว ไม่ได้อ้างความแม่นยำของ AI

## สถานะการตรวจล่าสุด

ตามคำขอของผู้ใช้ หยุดเพิ่มและรันทดสอบระหว่างเก็บงานสุดท้าย ชุด Python ที่รันไปก่อนคำขอนั้นผ่าน 66 กรณี ส่วน SQL รอบล่าสุดพบ UUID ในข้อมูลทดสอบเขียนไม่ครบ ได้แก้ข้อมูลดังกล่าวแล้วแต่ยังไม่ได้รันซ้ำ การแก้ไขช่วงท้ายและหน้าจอจึงยังต้องตรวจบน staging ก่อนเปิดรับเงินจริง ไม่มีการอ้างว่าการตรวจทั้งหมดผ่านแล้ว
